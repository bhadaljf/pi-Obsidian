第一阶段：先搞懂 Pi 的“心脏”

今天先只看这 3 个：

```
packages/coding-agent/src/core/agent-session.ts
packages/coding-agent/src/core/agent-session-runtime.ts
packages/coding-agent/src/core/agent-session-services.ts
```

实际仓库里确实存在这三个文件，其中 `agent-session.ts` 很大，大约 120KB，所以不要从第一行读到最后一行。

阅读顺序：

```
① agent-session.ts
        ↓
② agent-session-runtime.ts
        ↓
③ agent-session-services.ts
```

但是第一遍的目标不是“看懂代码”，而是回答这 5 个问题：

```
1. AgentSession 是什么？
2. 一次用户请求从哪里进入？
3. 它在哪里调用 LLM？
4. LLM 返回 Tool Call 后，谁负责执行 Tool？
5. Tool 执行完之后，结果怎么重新交给 LLM？
```

你最终应该能自己画出：

```
用户
 ↓
AgentSession
 ↓
LLM
 ↓
Tool Call
 ↓
Tool
 ↓
Tool Result
 ↓
LLM
 ↓
……
 ↓
最终回答
```

如果这条链你能在源码里找到，Pi 的核心就已经打开一半了。

第二阶段：再看真正的 Agent Runtime

接下来重点：

```
packages/coding-agent/src/core/agent-session-runtime.ts
```

这个文件名字已经非常明确：

`Agent Session Runtime`

也就是：

> Agent Session 实际运行时所需要的那部分逻辑。

你重点找：

```
runtime
event
prompt
assistant
tool
stream
```

相关的方法和类型。

不要纠结每一行 TypeScript。

你要搞清楚：

```
“谁在驱动 Agent 一轮一轮地运行？”
```

这比知道某个工具函数怎么写重要得多。

第三阶段：看 Tool 到底怎么进入 Agent

等你搞懂 AgentSession 后，再去看：

```
packages/coding-agent/src/core/
```

里面的 Tool 相关代码。

你现在已经可以确认这个目录里至少有：

```
bash-executor.ts
exec.ts
event-bus.ts
```

这些真实存在。

然后再找具体的：

```
read
write
edit
bash
```

相关实现。

你要回答：

> LLM 怎么“知道”自己可以调用 read/bash/edit？

这是 Coding Agent 和普通 Chatbot 最大的区别之一。

第四阶段：再看 Extension

这一步非常重要，因为你刚才一直在问 Pi 为什么“不内置 MCP / Plan / Todo / Sub-agent”。

实际仓库里有：

```
packages/coding-agent/src/extensions/
```

以及：

```
packages/coding-agent/src/core/extensions/
```

所以这里不要凭 README 猜，直接研究实际 Extension 机制。

重点回答：

```
Extension 怎么加载？

Extension 能监听什么事件？

Extension 能增加 Tool 吗？

Extension 能修改 Agent 行为吗？

Extension 能修改 UI 吗？

Extension 能访问 Session 吗？
```

等你理解这里，就能真正理解 Pi 为什么敢说：

```
No MCP
No Plan
No Todo
No Sub-agent
```

因为你会看到它到底给 Extension 留了多大的空间。

第五阶段：Session

之后再看：

```
session
```

相关实现。

你前面已经读过：

```
/tree
/compact

```

所以这一阶段你要把这些东西和源码对应起来：

```
Session
│
```

这些问题弄懂以后，你对 Pi 的 Session 架构就基本清楚了。
